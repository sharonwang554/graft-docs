# README sync pipeline: research notes

Researched 2026-10-18 against primary sources: docs.github.com (fetched as Markdown from the docs article API), source and docs in the action repos at the tags named below, vercel.com/docs, docs.astro.build (withastro/docs source), and npm registry metadata. Claims marked **UNVERIFIED** could not be confirmed from a primary source. Claims marked **Tested** were checked by hand on 2026-10-18.

Versions at time of writing: `anthropics/claude-code-action` v1 = v1.0.252 (`f27be6b65a4652f08a2ba3cff79114829b588967`), `peter-evans/create-pull-request` v8.1.1 (`5f6978faf089d4d20b00c7766989d076bb2fc7f1`), `actions/create-github-app-token` v3.3.0 (`64ab729a6294000f5aa4a4bc0b73d1f32bc45510`), `actions/checkout` v7.0.1 (`3d3c42e5aac5ba805825da76410c181273ba90b1`). This repo has Astro 7.4.0 and **Starlight 0.42.6** installed (not 0.41; see `package.json`).

## Recommendations

**Pipeline shape**

1. **Triggers.** One workflow, `sync-upstream.yml`, with `schedule` (off the hour, for example `cron: "23 */6 * * *"`), `workflow_dispatch`, and optionally `repository_dispatch`. Add `concurrency: { group: sync-upstream, cancel-in-progress: false }`. Scheduled runs use the latest commit on `main` only.
2. **Detection** (cheap, stateless). Call `GET /repos/trailhq/Trail-Code/commits?path=README.md&per_page=1` with `GITHUB_TOKEN`, and do the same for `path=assets`. Compare the result with the SHA already stored in `src/data/source.json`, and exit early when nothing changed. At 4 to 8 calls a day, the 1,000 requests/hour `GITHUB_TOKEN` limit doesn't matter, so ETag caching across runs isn't worth the extra `actions/cache` state. If you want one call instead, `GET /repos/{o}/{r}/compare/{storedSha}...main` returns the changed file list. Don't poll `raw.githubusercontent.com`: its caching is undocumented (`max-age=300` observed) and it falls under the stricter unauthenticated limits.
3. **Regeneration** (deterministic). Check out upstream at the detected SHA with `actions/checkout` (`repository: trailhq/Trail-Code`, `ref: <sha>`, `path: upstream`; the default token works for a public repo). Then run the manifest-driven script. It should exit with a distinct code or output when the README's heading set differs from the manifest.
4. **LLM step, only on structure drift.** Run `anthropics/claude-code-action@<v1 SHA>` with a `prompt` (automation mode). Give it a narrow tool list in `claude_args`: `--allowedTools "Read,Edit,Glob,Grep"` (no `Bash`, no `gh`, no git push) plus `--max-turns`. Better still, use `--json-schema` so Claude returns the new manifest as `structured_output`, and have a deterministic step validate it and write the file. After that, re-run the generator and the tests.
5. **PR creation** in a separate step: `peter-evans/create-pull-request@<v8 SHA>` with a fixed `branch: sync/upstream-readme`, so repeat runs update one PR. Give it a token from `actions/create-github-app-token@<v3 SHA>`, which uses a small GitHub App you create with Contents RW and Pull requests RW. With an App token, `deploy.yml` (Vale and build) runs on the PR without approval. `GITHUB_TOKEN` would also work, but each PR's CI would then wait for someone to click **Approve workflows to run**.
6. **Deploy.** A human merges, the merge is a push to `main`, and Vercel's Git integration deploys it. If bot-authored merge commits ever fail to deploy, add a Vercel Deploy Hook (`curl -X POST`) as a post-merge step or fallback.
7. **Mermaid.** Replace the hand-written `public/assets/graft-architecture.svg` with `astro-mermaid@2.1.0` plus `mermaid@^11`, registered **before** `starlight()`. The generator then copies the README's mermaid fence through verbatim.

**Gotchas that shape these choices**

- **60-day auto-disable.** "In a public repository, scheduled workflows are automatically disabled when no repository activity has occurred in 60 days." GitHub doesn't define "activity". Whether pushes made with `GITHUB_TOKEN` or by bots count is **UNVERIFIED**. If upstream stays quiet for 60 days and nobody pushes here, the schedule stops silently. You can re-enable it with `gh workflow enable sync-upstream.yml` or `PUT /repos/{owner}/{repo}/actions/workflows/{id}/enable`, and you can monitor `state == "disabled_inactivity"` through `GET .../actions/workflows`. Committing a change to the `cron` line also reactivates the schedule. This repo's last push was 2026-08-21 (`pushed_at`), so it has already been quiet for about 58 days.
- **Scheduled-run actor.** A scheduled run's `actor` is the user who last changed the `cron` line. claude-code-action rejects bot actors on every event, schedules included. So the cron line must be last edited by a human, or the bot must be listed in `allowed_bots`.
- **`GITHUB_TOKEN` events.** Pushes and PRs made with `GITHUB_TOKEN` don't trigger `push` workflows. Since June 2026, PRs created with it get approval-gated `pull_request` runs. `workflow_dispatch` and `repository_dispatch` are the exceptions that always run.
- **claude-code-action doesn't open PRs by default.** When the action uses its own Claude App token, it revokes that token at the end of the step, so a later step can't reuse it. Its default auth also needs the Claude GitHub App installed and `id-token: write`. It skips the run (`workflow_not_found_on_default_branch`) when the workflow file isn't on the default branch, so test only after merging, or pass your own `github_token`.
- **Prompt injection.** The upstream README is untrusted input. Keep the LLM's tools minimal, have deterministic code validate its output, and require a human merge.
- **Playwright on Vercel.** Vercel builds on Amazon Linux 2023, and Playwright lists only Debian/Ubuntu as supported Linux. That rules out `rehype-mermaid`, which needs Playwright, inside Vercel builds. `rehype-mermaid` would also need you to switch Astro 7 from its default Sätteri processor to `unified()`.
- **`mermaid@latest` is 12.2.0**, but `astro-mermaid` declares `peerDependencies: mermaid "^10.0.0 || ^11.0.0"`. Pin `mermaid@^11`.

## 1. GitHub Actions `schedule`, `workflow_dispatch`, `repository_dispatch`

Source for all quotes unless noted: [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

- **Minimum interval:** "The shortest interval you can run scheduled workflows is once every 5 minutes."
- **Delays and drops:** "The `schedule` event can be delayed during periods of high loads of GitHub Actions workflow runs. High load times include the start of every hour. If the load is sufficiently high enough, some queued jobs may be dropped. To decrease the chance of delay, schedule your workflow to run at a different time of the hour."
- **Branch:** "Scheduled workflows will only run on the default branch." "Scheduled workflows run on the latest commit on the default branch." (`GITHUB_SHA` = "Last commit on default branch".)
- **Timezone:** UTC by default. A per-schedule `timezone:` (IANA string) is now supported, with DST spring-forward runs moved to the next valid time. The `@daily`-style shortcuts aren't supported.
- **60-day rule:** "In a public repository, scheduled workflows are automatically disabled when no repository activity has occurred in 60 days." The [disable/enable page](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows) repeats this and adds: "When a public repository is forked, scheduled workflows are disabled by default."
- **What counts as activity:** **UNVERIFIED.** Neither page defines it, and I found no GitHub statement on whether `GITHUB_TOKEN` or `github-actions[bot]` pushes count. Inference: scheduled runs themselves can't count, or the rule would never trigger. Community keepalive actions that make dummy commits exist, but they're not primary sources. The best-known one (`gautamkrishnar/keepalive-workflow`) currently returns HTTP 403 "Repository access blocked" (reason `tos`) through the API, so don't build on that approach.
- **Reactivation through cron edit:** "For a deactivated scheduled workflow, if a user with `write` permissions to the repository makes a commit that changes the `cron` schedule on the workflow, the workflow will be reactivated, and that user will become the `actor` associated with any workflow runs." ([same page, `actor` for scheduled workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#actor-for-scheduled-workflows))
- **Notifications:** "Notifications for scheduled workflows are sent to the user who last modified the cron syntax in the workflow file."
- **Re-enable through UI or CLI:** Actions tab, select the workflow, then **Enable workflow**; or `gh workflow enable WORKFLOW` ([source](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows#enabling-a-workflow)).
- **Re-enable through REST:** `PUT /repos/{owner}/{repo}/actions/workflows/{workflow_id}/enable` "Enables a workflow and sets the state of the workflow to active. You can replace workflow_id with the workflow file name." It returns 204 ([REST workflows](https://docs.github.com/en/rest/actions/workflows#enable-a-workflow)). The workflow `state` enum includes `disabled_inactivity`. Permissions: classic PAT needs `repo`; fine-grained PAT or GitHub App needs repository **Actions: write** ([fine-grained PAT table](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens), [GitHub App table](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps)). Whether calling `enable` on an already-active workflow resets the 60-day timer is **UNVERIFIED**.
- **`workflow_dispatch`:** "This event will only trigger a workflow run if the workflow file exists on the default branch." "Once a workflow has run at least once, you can dispatch it against any branch or tag via the GitHub API or GitHub CLI." Limits: 25 top-level `inputs` and a 65,535-character payload ([source](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch)). The REST dispatch endpoint needs **Actions: write**.
- **`repository_dispatch`:** "You can use the GitHub API to trigger a webhook event called `repository_dispatch` when you want to trigger a workflow for activity that happens outside of GitHub." It runs on the default branch, `event_type` is limited to 100 characters, `client_payload` to 10 top-level properties and 65,535 characters ([source](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#repository_dispatch)). `POST /repos/{owner}/{repo}/dispatches` needs repository **Contents: write** (fine-grained PAT or App).
- **Related (public repos):** Since 2026-07-28, GitHub "holds" runs it identifies as potentially malicious on public github.com repos until a write collaborator approves them. The triggering events aren't specified ([changelog](https://github.blog/changelog/2026-07-28-github-actions-holds-potentially-malicious-workflows-for-approval/)).

## 2. `GITHUB_TOKEN`-triggered events and workarounds

- **Exact wording** ([GITHUB_TOKEN concept](https://docs.github.com/en/actions/concepts/security/github_token#when-github_token-triggers-workflow-runs); the same text appears in [Triggering a workflow from a workflow](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow)):
  > When you use the repository's `GITHUB_TOKEN` to perform tasks, events triggered by the `GITHUB_TOKEN` will not create a new workflow run, with the following exceptions:
  > * `workflow_dispatch` and `repository_dispatch` events always create workflow runs.
  > * `pull_request` events with the `opened`, `synchronize`, or `reopened` activity types: when a workflow using `GITHUB_TOKEN` creates or updates a pull request, the resulting `pull_request` event creates workflow runs in an **approval-required** state. ... a user with write access to the repository can start the runs by selecting **Approve workflows to run**. Other `pull_request` activity types (such as `labeled`, `edited`, or `closed`) do not create workflow runs.
  >
  > ... if a workflow run pushes code using the repository's `GITHUB_TOKEN`, a new workflow will not run even when the repository contains a workflow configured to run when `push` events occur.
- The approval-required behavior is new as of 2026-06-11: "Pull requests created by the `github-actions[bot]` are now able to run your CI/CD workflows with user approval" ([changelog](https://github.blog/changelog/2026-06-11-bot-created-pull-requests-can-run-workflows-if-approved/)). Third-party docs written earlier, including peter-evans' "cannot trigger other workflows", predate this change.
- **Recommended workaround:** "If you do want to trigger a workflow from within a workflow run, you can use a GitHub App installation access token or a personal access token instead of `GITHUB_TOKEN` ... Using one of these alternatives also lets `pull_request` workflows run automatically (without the approval prompt described above)" ([source](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow)).
  - [`actions/create-github-app-token`](https://github.com/actions/create-github-app-token) v3 takes `client-id` (the legacy `app-id` is still accepted) and `private-key`. "An installation access token expires after 1 hour."
  - [peter-evans/create-pull-request concepts](https://github.com/peter-evans/create-pull-request/blob/main/docs/concepts-guidelines.md#triggering-further-workflow-runs): a GitHub App token "will trigger both `on: push` and `on: pull_request` workflows". It calls a PAT from a dedicated machine account "the standard workaround". Fine-grained PAT or App scopes it lists: `contents: write`, `pull-requests: write`.
- **Permissions with `GITHUB_TOKEN`:** declare `permissions: { contents: write, pull-requests: write }` ([workflow syntax `permissions`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)). New personal-account repos default to read-only: "By default, when you create a new repository in your personal account, `GITHUB_TOKEN` only has read access for the `contents` and `packages` scopes." ([repo Actions settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository#configuring-the-default-github_token-permissions))
- **Repo setting:** "By default, when you create a new repository in your personal account, workflows are not allowed to create or approve pull requests." To change it: Settings > Actions > General > Workflow permissions > "**Allow GitHub Actions to create and approve pull requests** setting to configure whether `GITHUB_TOKEN` can create and approve pull requests" ([source](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository#preventing-github-actions-from-creating-or-approving-pull-requests)). peter-evans' README says the same: "For this action to work you must explicitly allow GitHub Actions to create pull requests." The setting only governs `GITHUB_TOKEN`. I couldn't read this repo's current value (the API returned 403 with the local `gh` token).
- REST `POST /repos/{owner}/{repo}/pulls` needs **Pull requests: write**.

Inference, not documented as a pattern. That sanitizing applies to GitHub comment and issue context. A README file that Claude reads from disk isn't covered (inference). It's still upstream-controlled text.
- **Structured outputs:** "Get validated JSON results from Claude that automatically become GitHub Action outputs", through `--json-schema` in `claude_args` ([usage.md#structured-outputs](https://github.com/anthropics/claude-code-action/blob/v1.0.252/docs/usage.md#structured-outputs)). This is the cleanest way to have the LLM propose a manifest without write tools.

## 4. Cheap change detection for one upstream file

- **List commits by path:** `GET /repos/{owner}/{repo}/commits`, where `path` means "Only commits containing this file path will be returned" ([REST commits](https://docs.github.com/en/rest/commits/commits#list-commits)). **Tested:** `?path=README.md&per_page=1` on trailhq/Trail-Code returned `de4d2018825c71295b1a8235a99d69ef9b3c488c` (2026-10-15), with a weak `ETag` and a `Last-Modified` header.
- **Contents blob SHA:** `GET /repos/{owner}/{repo}/contents/{path}` returns the file's git blob `sha` (README: `68a6a061...`, size 60,002 bytes). Files of 1 MB or smaller support every feature; for 1 to 100 MB use the `raw` or `object` media type ([REST contents](https://docs.github.com/en/rest/repos/contents#get-repository-content)). The blob SHA changes only when the content changes. The commit SHA is better for provenance (`source.json`).
- **Compare** (one call for "did README or assets change since X"): `GET /repos/{owner}/{repo}/compare/{basehead}` lists changed files, "up to 300 changed files for the entire comparison" ([REST compare](https://docs.github.com/en/rest/commits/commits#compare-two-commits)). **Tested:** `ead585b...main` returns `status: identical`, so the site is currently in sync.
- **Conditional requests:** "Making a conditional request does not count against your primary rate limit if a `304` response is returned and the request was made while correctly authorized with an `Authorization` header" ([best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#use-conditional-requests)). **Tested:** authenticated `If-None-Match` got 304 and `x-ratelimit-remaining` stayed at 4956 across 2 calls; unauthenticated 304s decremented it (58, then 57). Persisting ETags between Actions runs would need `actions/cache` or a committed file. Not worth it at this polling rate.
- **Rate limits** ([REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)): unauthenticated "60 requests per hour", "associated with the originating IP address" (GitHub-hosted runner IPs are shared, so this can be exhausted by others; inference). "The rate limit for `GITHUB_TOKEN` is 1,000 requests per hour per repository." PATs get 5,000 per hour, and App installations at least 5,000 per hour.
- **Reading another public repo with `GITHUB_TOKEN`:** `actions/checkout` with `repository: other/repo` works for public repos without extra tokens. Only "If your secondary repository is private or internal" do you need a PAT ([checkout README](https://github.com/actions/checkout#checkout-multiple-repos-side-by-side)).
- **raw.githubusercontent.com:** caching isn't documented by GitHub (**UNVERIFIED** as policy). **Observed:** `cache-control: max-age=300`, Varnish `x-cache: HIT`. GitHub's 2025-05-08 changelog says new unauthenticated limits apply to "downloading files from raw.githubusercontent.com" ([changelog](https://github.blog/changelog/2025-05-08-updated-rate-limits-for-unauthenticated-requests/)). Use the API, or `actions/checkout` at a pinned SHA, instead.

## 6. Vercel Git integration with bot commits, and Deploy Hooks

- **Author verification is scoped to private repos:** "As an additional security measure, commits on private Git repositories (and commits of forks that are targeting those Git repositories) will only be deployed if the commit author also has access to the respective project on Vercel." "This only applies to commit authors on GitHub organizations, GitLab groups and non-personal Bitbucket workspaces. It does not apply to collaborators on personal Git accounts." "For public Git repositories, a different behavior applies." ([Vercel Git docs](https://vercel.com/docs/git#deploying-private-git-repositories)). `sharonwang554/graft-docs` is public and on a personal account, so per these docs, bot-authored commits on `main` should deploy.
- **Hobby wording conflict:** the docs' Hobby section, under the private-repo heading, says "the commit author must be the owner of the Hobby team." A Vercel KB guide (updated 2026-10-16) says more broadly: "On a Hobby account, only the account owner can trigger deployments, and contributors who aren't the owner cannot deploy" ([KB](https://vercel.com/kb/guide/why-aren-t-commits-triggering-deployments-on-vercel)). Whether a `github-actions[bot]`- or App-authored commit on a public personal repo deploys on a Hobby project is **UNVERIFIED**. The project's plan isn't known from the repo. Check the first bot PR's merge. A human pressing **Merge** makes a merge commit authored by that human, but how authorship works per merge method wasn't checked in GitHub docs (**UNVERIFIED**).
- **Fork protection:** "when you receive a pull request from a fork of your repository, Vercel will require authorization from you or a team member to deploy the pull request" ([source](https://vercel.com/docs/git#deploying-forks-of-public-git-repositories)). It can be turned off under "Git Fork Protection" in Project Settings > Security ([Vercel for GitHub](https://vercel.com/docs/git/vercel-for-github#deployment-authorizations-for-forks)). Same-repo bot branches aren't forks, so this shouldn't apply (inference).
- **Deploy Hooks:** "Deploy Hooks allow you to create URLs that accept HTTP `POST` requests to trigger deployments ... uniquely linked to your project, repository, and branch, so there is no need to use any authentication mechanism." "This allows anyone with the URL to deploy your project, so treat it with the same security as you would any other token." Limits: 5 hooks per project (Hobby or Pro), "up to 60 times per hour per project". Deploy Hooks don't fire with `github.enabled = false` in `vercel.json` ([Deploy Hooks](https://vercel.com/docs/deploy-hooks)). Store the URL as an Actions secret and call it after merge, for example in a `push: main` job, only if Git-integration deploys turn out to skip bot commits.
- **Limits:** Hobby allows 100 deployments per day ([KB](https://vercel.com/kb/guide/why-aren-t-commits-triggering-deployments-on-vercel)). A single sync PR per upstream change stays well under that.

## 7. Prior art using GitHub features

- **GitHub Agentic Workflows (`gh aw`)**, "Made by GitHub Next & Microsoft Research": Markdown-defined agent workflows compiled to Actions, with engines including Claude Code. Writes go through `safe-outputs`, including `create-pull-request`: "Only the writes you declared are applied, by a separate job with its own permissions", after a threat-detection job ([gh-aw](https://github.github.com/gh-aw/), [safe outputs](https://github.github.com/gh-aw/reference/safe-outputs/)). This is the same "agent proposes, separate permissioned job writes" split recommended above. Since 2026-06-11 it can run on the built-in `GITHUB_TOKEN` ([changelog](https://github.blog/changelog/2026-06-11-agentic-workflows-no-longer-need-a-personal-access-token/)).
- **Dependabot `gitsubmodule`:** add Trail-Code as a submodule and Dependabot opens PRs that bump it on `daily`, `weekly`, or `cron` schedules ("Dependabot tracks the latest commit on the configured branch", [options reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference)). This avoids the 60-day schedule problem, but on Dependabot-triggered runs "`GITHUB_TOKEN` has read-only permissions by default" and "GitHub Actions secrets are not available" ([Dependabot on Actions](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-on-actions)). Regenerating pages onto Dependabot's branch would therefore need extra plumbing. Vercel's submodule handling wasn't checked (**UNVERIFIED**).
- **Upstream-pushed `repository_dispatch`:** the event-driven version, where upstream's workflow POSTs `/repos/sharonwang554/graft-docs/dispatches`. It needs a token with Contents: write on our repo stored in upstream's secrets. We don't control upstream, so it isn't available today.
- **claude-code-action "Documentation Sync on API Changes"** ([solutions.md](https://github.com/anthropics/claude-code-action/blob/v1.0.252/docs/solutions.md#documentation-sync-on-api-changes)): same-repo and PR-triggered. Useful for prompt and permission shape only.
