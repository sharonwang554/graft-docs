# AGENTS.md

This is the single source of truth for agent instructions in this repo. `CLAUDE.md` imports this file, so edit here, not there.

## Project

A community documentation portal for [Trail-code](https://github.com/trailhq/Trail-Code) (previously Graft), deployed at https://graft.sharonwang.me. Built with Astro Starlight, deployed statically to Vercel.

## Commands

Node version is pinned in `.nvmrc` (`nvm use`).

```bash
npm install
npm run dev        # http://localhost:4321
npm run test:run   # Vitest: structure, frontmatter, sidebar, build
npm run build
npm run preview
```

CI (`.github/workflows/deploy.yml`) runs Vale on `src/content/docs` and `npm run build` on every push and PR. Pushes to `main` deploy via Vercel.

## Layout

- `src/content/docs/`: all pages, organized by [Diataxis](https://diataxis.fr/): `tutorials/`, `how-to/`, `reference/`, `explanation/`, and `index.mdx`.
- `astro.config.mjs`: the sidebar. Tutorials are listed by slug, and the other three sections are autogenerated. Redirects for renamed pages live here too.
- `src/components/`: Starlight overrides (`Banner`, `Footer`, `Head`).
- `src/data/source.ts`: the upstream commit and pull date shown in the banner.
- `src/pages/llms.txt.ts`, `src/pages/llms-full.txt.ts`, `src/lib/llms.ts`: generate `/llms.txt` and `/llms-full.txt` at build time.
- `tests/`: Vitest checks that expected pages exist, that frontmatter is valid, and that the site builds.

## Conventions

- Every `.mdx` page needs `title` and `description` frontmatter, and a `lastUpdated` date. Use `sidebar.order` to order pages within a section.
- Put each page in the right Diataxis section. Tutorials teach, how-tos solve a task, reference describes, and explanation discusses.
- Content comes from the upstream Trail-code README. When re-syncing, update `src/data/source.ts` and the `lastUpdated` of each changed page.
- When you add, rename, or remove a page, update `tests/pages.test.ts`. If it's a tutorial, also update the sidebar in `astro.config.mjs` and `tests/sidebar.test.ts`. Add a redirect for a renamed page.
- The product is "Trail-code" in prose. The CLI is `trail`, and "graft map" refers to the code graph.
- Prose must pass Vale (`.vale.ini`).
- Commits use Conventional Commits (`docs:`, `feat:`, `chore:`, `ci:`, `refactor:`).

## Trail — repo context graph

This repo is indexed in `.trail/cache/`: small linked markdown nodes that explain each
system and carry exact file:line spans, kept in sync with the code through git.

For ANY task here — understanding how something works, finding where code lives,
or scoping a change — get context from the graph before grepping or opening
source files. Re-ask freely (it's cheap) and reuse literal identifiers you
already have (symbol, error string, file name) as the query. New to this repo?
Run `trail map` first — a token-budgeted orientation (dir clusters, hubs,
hotspots), no LLM, no key.

- Run `trail ask "<your question>" --source` → ranked nodes with the relevant
  code spans inlined (each hit's ≤8-line crux by default; `--full` for whole
  definitions when the crux isn't enough). Match the tool to the task shape:
  for understanding or editing, the top node IS the answer — cite its
  `covers:` file:line spans and edit straight from `--source`. For
  exhaustive tasks ("every occurrence / every caller of this pattern"), ranked
  results are top-N, not complete — run `trail grep "<literal>"` instead
  (exhaustive over indexed files, grouped by enclosing symbol), falling back
  to raw `grep -rn` only for unindexed files.
- `trail skeleton <file>` → every definition's signature + span, ~10× cheaper
  than reading the file; use it to skim an API surface.
- `trail callers <symbol>` gives precomputed, exact edges — who calls this.
  Add `--direction out` for what it calls, or `--depth N` to walk
  transitively for the full blast radius. For structural questions, skip
  ranking and use this directly.
- Or browse: `.trail/cache/INDEX.md` lists every node; follow the links.
- Monorepos and folders of multiple repos rank fairly across sub-projects —
  hits carry `[scope/]` labels naming which one they're from. Narrow with
  `trail ask "<task>" --in <scope>/` once you know where you're working.

If a returned span is truncated ("+N more lines"), open the file at that exact
range before finalizing. Only open source files when a node genuinely lacks a
needed detail, and then at the exact file:line the node points to — never
re-read whole files.

After big code changes, refresh the graph with `trail build` (deterministic,
no API key, $0).
